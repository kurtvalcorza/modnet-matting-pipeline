#### Description

`XM5354/Modnet_models` at revision `71aca6d04ed0267b4b12bde776868f2b9fb1d06f` mirrors `modnet_photographic_portrait_matting.ckpt` (26,255,603 bytes, SHA-256 `7c22235f…`), the authors' photographic portrait-matting checkpoint of MODNet (Ke, Sun, Li, Yan and Lau, AAAI 2022), published on Google Drive from the upstream repository `ZHKKKe/MODNet`. MODNet decomposes trimap-free matting into three sub-objectives learned jointly: a **low-resolution branch** (a MobileNetV2 feature extractor with an SE block and two 5 × 5 convolutions) predicts the coarse portrait semantics at 1/16 scale; a **high-resolution branch** (32 channels, fed with the image at 1/2 and 1/4 scale and the encoder's first two stages) predicts the boundary detail; a **fusion branch** combines both into the alpha matte at input resolution through a sigmoid. Norm layers are `IBNorm` (BatchNorm on half the channels, InstanceNorm on the other half). The network has 6,487,075 parameters in float32 (the backbone is registered twice in the state dict, once under `backbone` and once inside the low-resolution branch; the pipeline stores it once). At inference the image is normalised to [−1, 1], resized so that its short side is 512 (unless it already straddles 512) with both sides multiples of 32, and the matte is resized back to the input size; the paper reports the model trained on the authors' proprietary portrait dataset with supervised objectives on each branch (their public training script `src/trainer.py` gives the losses), and fine-tuned on unlabelled video with a self-supervised sub-objective consistency (SOC) that this repository does not vendor.

What this repository adds is the `ModNetMattingPipeline` class in `src/modnet_matting_pipeline/pipeline.py`: manifest verification of the one-file Hub snapshot before any model library is imported (`verify_snapshot`, which also checks the converted file against its pinned digest when present), fresh-clone staging at the pinned revision (`stage_missing_files`), a **static audit of the pickle** that recognises torch's zip, plain and legacy five-stream layouts, lists every global with `pickletools` and refuses anything outside the allow-list (`audit_pickle`, digest pinned), a **one-time conversion** through torch's weights-only unpickler into a strictly loaded model whose state dict is saved as safetensors with the aliased backbone stored once (`convert_model`), construction of the architecture from the vendored `modeling.py` (`build_model`), record validation with named ceilings (`validate_inputs`, `validate_dataset`), trimap-free matting at any input size with the upstream resize rules (`predict`), per-image MAD / MSE / SAD and unknown-band MAD against the constant baselines (`evaluate`), an upstream-style trimap from a reference alpha (`trimap_from_alpha`), bounded fine-tuning of the matting branches — optionally also the backbone — with the upstream supervised losses and frozen BatchNorm statistics (`adapt`), and a safetensors adapter artifact that is digest-verified and scope-checked before deserialization (`save_artifact`, `from_artifact`). `samples.py` renders the labelled portraits deterministically, loads a user's photograph (`load_photo`), splits records, loads a BYOD zip through the archive API (no `extractall`) and writes pairs in that shape; `metrics.py` holds the matte metrics and the baselines; `modeling.py` is the vendored architecture.

Two things about this profile are stated rather than hidden. **The labelled data are drawings**: figures with head, shoulders, a hair cap and dozens of fractional-coverage hair strands over generated backgrounds, chosen because P3M-10k, PPM-100 and AIM-500 are research-only and photographs of identifiable people carry consent obligations this repository cannot discharge; the frozen numbers are out-of-domain and the adaptation gain is large by construction. **The default path never sees a photograph**: the four CC0 Commons portraits first pinned for a label-free sanity check could not be fetched from a shared cloud runtime (HTTP 429) and were removed rather than re-hosted; a real portrait is matted only when the user supplies one, and the build record's observation on such photographs (the adapted model taking in dark background beside a subject) is reported below as what to expect.

#### Intended Use and Limitations

###### Primary Intended Uses

Two tasks are exposed. **Portrait matting:** input is an RGB image (uint8 array or file; both sides in [64, 4096]); output is an alpha matte in [0, 1] at the input size, the resized model input size and the foreground fraction — the matte can be used to cut the subject out or to composite it over another background. **Adaptation to labelled portraits:** given at least four 512 × 512 image/alpha pairs, the pipeline fine-tunes the matting branches (optionally also the backbone) with the upstream supervised losses, a small learning rate and validation-loss epoch selection, mattes with the adapted model and exports the changed tensors as a 17 MB adapter. Envisioned application domains are background replacement and cut-out generation for portraits in photography, video-conferencing prototypes and creative tools; teaching and evaluating matting fine-tuning; and prototyping a matting service whose quality is then measured against the operator's own mattes. In a larger system the pipeline is a single-image matting component and an adaptation baseline whose mattes feed a compositor or an editor's review; it is not a video matting system, a face detector, or a segmentation model for anything but a portrait's subject.

###### Primary Intended Users

Intended users are computer-vision engineers, imaging and creative-tool developers, and machine-learning practitioners who work with portrait photographs, in research, product prototyping or the DIMER model workbench. The pipeline assumes its users understand that a matte's value is in its fractional band (hair, soft edges) and that whole-image MAD is dominated by the easy interior; that MODNet was trained on photographic portraits of one person against a background and knows nothing else; that a labelled alpha must belong to its image and mark the subject the operator means; that fine-tuning on a narrow domain moves the model everywhere, which the photographs after adaptation are there to show; and that a 20-portrait evaluation on drawings is a contract check, not a measurement of matting skill.

###### Out-of-scope use cases

1. **Capability boundary:** the pipeline mattes single portraits and fine-tunes the matting branches on labelled pairs. It does not matte video (no temporal consistency), does not run the paper's self-supervised SOC adaptation, does not take a trimap, does not detect or recognise faces, does not judge composite quality, and does not reproduce the published PPM-100 scores.
2. **Input boundary:** inference images are RGB uint8 with both sides in [64, 4096]; labelled records are exactly 512 × 512 with an alpha in [0, 1] and datasets hold 4..2,000 records with at least one non-background alpha. Other sizes for labelled records, alphas outside [0, 1], non-RGB arrays and empty datasets are not inputs.
3. **Decision boundary:** not for autonomous action on a matte — identity verification, surveillance, content moderation, or any decision about the person in the image — and not for producing composites presented as authentic photographs. A matte from this pipeline is an experiment output, not a verified cut-out.
4. **Provenance boundary:** not for settings that require the upstream serialized checkpoint to be executed as-is, that forbid any one-time unpickling of a third-party checkpoint even through a restricted loader after a static audit, or that require the weights to come from the authors' own distribution channel rather than a digest-verified mirror; the trust boundary is documented under *Mitigations* and in `docs/WEIGHTS.md`.

#### Factors

###### Groups

The inputs are photographs of people, so demographic factors are relevant and are **not measured here**: the authors do not publish the composition of their training portraits by skin tone, age, gender, hair type or head covering, and this repository evaluates on drawn figures (seven skin tones, eight hair colours, optional long hair and glasses, all cartoon); the four CC0 photographs used during the build (an elderly man with a beard and pipe, a veiled woman, an elderly woman, a young woman in a close-up) are not part of the tutorial. Matting quality is known to vary with hair type and texture (fine, curly or light hair against a similar background is the classic failure), with skin-tone/background contrast, with head coverings and accessories, and with more than one person in the frame; none of this is quantified in this repository. A deployment serving a population should measure matte quality per group on its own labelled photographs and own that measurement; whoever is under-represented in the authors' training portraits bears the error.

###### Instrumentation

The instrument is an ordinary RGB camera producing 8-bit images; a user's photograph is downscaled once to at most 1,536 pixels on the long side, and the labelled portraits are rendered at 1,024 × 1,024 and box-filtered to 512 × 512. The model's own instrument is its resize rule — the short side to 512 pixels, multiples of 32 — so fine hair is resolved at about 512-pixel resolution whatever the input, and the matte is interpolated back; compression artefacts, motion blur, low light, and colour casts reach the model as feature error and the pipeline detects none of them: validation checks shapes, dtypes and ranges, not image quality. Alpha references produced by another tool or a different edge-softness convention shift every error metric without any error being raised.

###### Environment

Operating environment: Python 3.12 with `torch==2.14.0`, `numpy==2.5.3`, `pillow==11.3.0`, `safetensors==0.8.0`, `huggingface-hub==1.32.0` (`pyproject.toml`); no torchvision, scipy or Hub-hosted module. The model is float32 as shipped and runs in float32 on CPU and CUDA (`device` defaults to CUDA when visible, CPU otherwise); the recorded runs are under *Runtime* (four 1536-pixel photographs matted in 0.12 s on an RTX 5070 Ti laptop GPU and 0.66 s on its CPU during the build; a 72-step adaptation in 13.4 s on the GPU and about 3 minutes on the CPU). Data environment: the model assumes a single portrait subject against a background, photographic, roughly frontal; it degrades, without any error, on drawings (the tutorial's point), on groups, on full-body shots with the subject small in the frame, on hands and objects in front of the body, and on backgrounds that share the subject's colour.

#### Metrics

###### Performance Measures

The pipeline reports, exactly as `metrics.matting_metrics` names them, per image and then averaged over the records scored: `mad` (mean absolute difference between predicted and reference alpha over every pixel), `mse`, `sad` (summed absolute difference divided by 1,000, the matting-literature convention), and `mad_unknown` (the MAD over the trimap's unknown band — every fractional-alpha pixel grown by 8 pixels — the region matting exists for). Four comparison points are read together: the **all-background** and **all-foreground constant mattes** (`constant_baselines`; all-background MAD equals the foreground fraction), the **frozen model** and the **adapted model**. The unknown-band MAD is the headline because whole-image MAD is dominated by the easy interior; MSE and SAD are kept because the literature reports them. On a user's photograph, which carries no reference, the notebook reports the foreground fraction and the mean absolute difference between the frozen and the adapted matte. Every number in this repository is sample-sanity evidence on 20 drawn test and 12 drawn validation portraits from one seeded run with no dispersion estimate; the PPM-100 benchmark of the paper is not reproduced or claimed.

###### Decision thresholds

The matte is the fusion branch's sigmoid output in [0, 1]; the pipeline applies no threshold and produces no binary mask. The limits fixed during development are input-contract limits, not decision thresholds — the inference size range, the 512 × 512 labelled-record size, the alpha range, the 4..2,000 record range, the 8-pixel trimap growth used only to compute the unknown-band metric and the training losses — chosen so that a rejection names a real defect and an acceptance never means "this alpha belongs to this image". An operator who needs a binary mask (a minimum alpha before a pixel counts as subject) or a quality gate (a maximum unknown-band MAD before a matte is accepted) must set it from verification against their own mattes, weighing a hole in the subject against a halo of background, and own it. `adapt` selects the epoch with the lowest validation loss, which is the only selection this repository performs.

###### Approaches to uncertainty and variability

Reported metrics come from one seeded run on **per-image averaged** held-out portraits — 20 drawn test portraits for the numbers, 12 drawn validation portraits for epoch selection only — with no cross-validation, bootstrap, ensemble or repeated-run averaging, and no dispersion is reported: with 20 portraits from one renderer, any interval would describe the renderer, not the model. A caller who needs one evaluates many photographs across hair types, backgrounds and framings and reports per-image distributions, and owns that design. Sources of run-to-run variability: the flip augmentation and shuffling are seeded (`numpy` generator), initialisation is the pinned checkpoint, and BatchNorm statistics are frozen; CUDA convolution kernels are not forced deterministic, so a re-run can differ in the last decimals of the adapted numbers (the frozen numbers differ between CPU and GPU only in the fourth decimal: test MAD 0.079384 vs 0.079514). The matte is the model's output and is **not a calibrated probability**; no per-pixel uncertainty beyond it is produced.

###### Mitigations

1. **Supply-chain integrity:** `MODEL_ID` and the 40-hex `MODEL_REVISION` are module constants; `verify_snapshot()` checks `modelId`, `revision`, and the byte size and SHA-256 of the manifest entry before any load, additionally asserts the checkpoint's digest against the package constant (which equals the authors' Google Drive file, verified 2026-09-20), and raises on the first mismatch (tests flip bytes, change the identity and delete the file and assert each raises). `stage_missing_files()` fetches only the manifest-listed file when absent, only at `MODEL_REVISION`, only when `allow_download=True`, and refuses a manifest naming another model. `.gitattributes` carries `weights/** -text`.
2. **Executable serialization handled explicitly (asset spec §11.2):** the pickle is not loaded by the runtime path. `audit_pickle` recognises the legacy torch layout, parses exactly its five header streams with `pickletools` (the storage bytes after them are never parsed), lists every global (`collections.OrderedDict`, `torch._utils._rebuild_tensor_v2`, `torch.FloatStorage`, `torch.LongStorage`) and refuses anything else; the audit digest is pinned. `convert_model` runs size → digest → audit before `torch.load(weights_only=True)` (torch's restricted unpickler, which cannot construct arbitrary objects), requires exactly 751 tensors under the `module.` prefix, checks the 312 aliased backbone tensors equal to their twins, and loads them with `strict=True` into the vendored `MODNet`; the model's state dict is re-saved as safetensors with the backbone once. Tests craft a zip archive with `os.system`, a plain pickle of a `complex`, and legacy files with `os.system` in the fourth and in the fifth stream, and assert each is refused before anything is unpickled.
3. **Deterministic, digest-pinned serving file:** `verify_converted` checks size and SHA-256 against `CONVERTED_SHA256` / `CONVERTED_BYTES` (reproduced by two build conversions and the executed notebook); the model loads with `strict=True` after `_expand_aliases` re-creates the twin keys, and a parameter-count check follows. With `require_source=False` (the DIMER-hosted case) the converted file alone is accepted, still digest-verified.
4. **Vendored, pinned architecture:** the model class is `modeling.py`, carried from `ZHKKKe/MODNet` at commit `28165a45…` with the three source files' digests recorded in `docs/WEIGHTS.md`; it contains no `torch.load`, no `exit()`, no `DataParallel`, and imports nothing but `torch`. No Hub-hosted Python is imported and no remote code runs.
5. **Data integrity:** nothing is downloaded but the checkpoint; the labelled portraits are rendered from seeds and their digest is recorded by `dataset_manifest`; a user's photograph is read once by Pillow and downscaled (`load_photo`); `load_byod_dataset` reads only the members `pairs.csv` names, through the archive API, writes nothing at a path taken from the archive, and caps the member count and archive size; `check_split_disjoint` refuses a record present in two splits by id or by image bytes.
6. **Artifact integrity and scope:** the adapter is safetensors, not a pickle. `load_artifact` validates the manifest **before** deserialising anything: the artifact format and `format_version`, the recorded base model id, revision and converted-base digest, exactly one weights entry named `adapter.safetensors` that resolves inside the artifact directory, an `adapter.trainable` that is exactly `branches` or `full`, and a tensor list equal to the exact set that scope may change on this model; the safetensors keys must then equal that set and every shape must match. The weights file's SHA-256 is checked against the adjacent manifest — it detects corruption or drift of the file relative to that manifest, not authenticity: an actor who can replace both files can make them agree.
7. **Input integrity:** `predict`, `evaluate`, `adapt`, `validate_inputs` and `validate_dataset` route through one checker, so their acceptance criteria cannot diverge; it rejects missing keys, non-uint8 or non-RGB arrays, sizes outside the inference range, labelled records that are not 512 × 512, alphas of the wrong shape, non-finite or outside [0, 1], duplicate ids and datasets whose alphas are all background.
8. **Training discipline:** only the declared scope receives gradients (the backbone stores no graph under `branches`), BatchNorm running statistics stay frozen (`freeze_norm`, as the upstream SOC code does), the learning rate defaults to 10⁻⁴, gradients are clipped at norm 1, the losses are the upstream supervised objective with its default scales, the epoch is selected by validation loss with the frozen model as epoch 0, and `adapt` is transactional — any failure restores the pre-adaptation tensors (aliases included), re-freezes the model and clears the adapter.
9. **Import boundary:** verification, the static audit and validation run before `torch`, `safetensors` or `huggingface_hub` are imported (DIMER RTM-001); `tests/test_import_boundary.py` fails if a rejected request reaches a model library, and an AST check fails if any of them is imported at module level outside the vendored `modeling.py`, which the pipeline imports lazily.
10. **Honest scope:** validation is labelled structural, the portraits are labelled drawings, the matte is labelled uncalibrated, the baselines are printed before any model number, the photograph gate is labelled a sanity check without a label, the notebook asserts only what the procedure guarantees plus the one directional claim the domain shift makes robust, and no upstream benchmark is claimed.

Not implemented, and therefore not claimed: no video matting, no SOC adaptation, no trimap input, no face detection, no calibration, no per-group evaluation, no evaluation on any photograph, and no measurement beyond the 80 drawn portraits.

###### Risks and harms

1. **A conversion can be subtly wrong:** the evidence is the strict key-and-shape match against the vendored architecture, the 312 alias tensors found equal, and sane mattes on four photographs during the build, under one torch version. A vendoring mistake that kept the parameter names while changing a branch's semantics would load strictly and silently compute something else; the recorded upstream file digests and the photograph sanity check are the controls.
2. **A pickle audit is an allow-list, not a proof:** the static audit bounds what the unpickler can name; torch's weights-only unpickler bounds what it can construct. The digest pins tie the audited bytes to the loaded bytes, and the unpickle happens once, in the operator's environment.
3. **Third-party mirror:** the staging source is a Hub re-upload by an unaffiliated account; its only guarantee is the byte-for-byte equality with the authors' Drive file that this repository verified and pinned. A different file at the same path can never load (digest pinned), but the mirror can disappear, and the Drive file has no immutable revision either.
4. **Demographic and hair-type bias:** matting errors concentrate on fine or light hair, low subject/background contrast, head coverings and accessories, and on whoever is rare in the unpublished training portraits; the operator sees no warning, and the person in the image bears the halo or the hole.
5. **Narrow fine-tuning moves the model everywhere:** the tutorial's adaptation to drawings changed the matte of the bearded man by 0.052 on average, taking in dark background beside the body; an operator who fine-tunes on one studio's portraits should expect the same on everyone else's.
6. **Consent, identity and misuse:** cut-outs of people enable composites, impersonation and covert profiling; the pipeline cannot tell a consented portrait from a scraped one, and photographs of identifiable people uploaded to a hosted runtime are personal data.
7. **In-domain optimism:** the drawn portraits are a domain shift by design; a reader who carries the adapted MAD of 0.004 to photographs draws an unsupported conclusion.
8. **Automation bias:** a clean-looking cut-out invites acting on it without review; the realistic confidentiality failure is a restricted photograph uploaded to a cloud notebook — inference is local, but the runtime may not be the operator's.

###### Use cases

The model must not be used for identity verification, surveillance, covert profiling, or any decision about a person in an image; it must not be used to produce composites presented as authentic photographs or to strip people from images without a lawful basis for processing them; it must not be used as evidence about MODNet's benchmark skill, which this repository does not measure; it must not be used to load or execute the upstream pickle in any way other than the audited, digest-verified, one-time conversion this repository performs; it must not be used to present the rendered portraits as photographs; and it must not be used in any way that breaches the Apache-2.0 terms of the upstream weights and code or the DIMER deployment terms.

## Input/output contract

- `ModNetMattingPipeline.from_pretrained(device=None, weights_dir=None, allow_download=False, require_source=True, report=None)`: stages and verifies the snapshot, audits and converts the checkpoint when the safetensors file is absent (reporting through `report`), builds the vendored architecture and loads the safetensors strictly. `require_source=False` accepts the digest-verified converted file without the checkpoint.
- `predict(records) -> dict` with `model` (id, revision, key, `adapted`), `output`, `predictions` (per record: `id`, `alpha` (H, W) float32 in [0, 1], `input_size`, `model_size`, `foreground_fraction`), `seconds`.
- `evaluate(records) -> dict`: `n_records`, `metric`, `model` (`n_images`, `mad`, `mse`, `sad`, `mad_unknown`), `per_image`, `baselines` (`all_background`, `all_foreground`, the same fields), `adapted`, `seconds`.
- `adapt(train, val=None, *, epochs=4, lr=1e-4, batch_size=4, trainable="branches", seed=0, progress=None) -> dict`: bounded Adam fine-tuning with the upstream losses; returns the trainable set and counts, hyperparameters, `losses`, `best_epoch`, per-epoch `history` (epoch 0 = the frozen model, each with `train_loss`, `train_loss_parts`, `val_loss` and the validation metrics) and `seconds`. `trainable="full"` also unfreezes the backbone.
- `save_artifact(output_dir, metadata=None) -> Path` writes `adapter.safetensors` (the trained tensors) + `manifest.json` (format, base model id/revision/key and converted digest, adaptation record, history, tensor names, file size and SHA-256); `from_artifact(...)` / `load_artifact(...)` verify all of that before deserialising.
- `validate_inputs(record) -> dict` (`id`, `shape`, `has_alpha`, `foreground_fraction`) and `validate_dataset(records, *, min_records=4, max_records=2000, require_labels=True) -> dict` (normalised `records`, counts, `sizes`, `foreground_fraction`, `fractional_alpha_fraction`, `digest`) raise exactly what the execution path would raise; `check_record` returns one normalised record; `trimap_from_alpha(alpha, radius=8)` the upstream-style trimap. `read_image(path)` / `read_alpha(path)` read files with Pillow; `render_portrait(seed)`, `sample_dataset(counts=None)`, `load_photo(path, record_id="photo")` are the data primitives; `load_byod_dataset(path)`, `write_sample_pair`, `write_dataset_csv` the BYOD I/O; `split_dataset`, `check_split_disjoint`, `dataset_manifest` the split helpers; `matte_errors`, `matting_metrics`, `constant_baselines` the metrics.
- `audit_pickle(path, allowed=…)`, `convert_model(path=None)`, `verify_converted(path=None)` and `build_model()` are the serialization primitives.
- Constants: `REF_SIZE = TRAIN_SIZE = 512`, `MIN_SIDE = 64`, `MAX_SIDE = 4096`, `MIN_RECORDS = 4`, `MAX_RECORDS = 2000`, `TRIMAP_RADIUS = 8`, `PARAMETER_COUNT = 6487075`, `STATE_TENSORS = 439`, `CHECKPOINT_TENSORS = 751`, `ADAPTATION_MODES = ("branches", "full")`, `ARTIFACT_FORMAT = "org.valcorza.modnet-matting.adapter.v1"`, `SOURCE_DRIVE_FILE_ID`, `UPSTREAM_CODE_COMMIT`, `SAMPLE_COUNTS = {"train": 48, "validation": 12, "test": 20}`.

## DIMER deployment notes

| Field | Status |
|---|---|
| **DIMER status** | **Planned / conditional** — the `.ckpt` asset-format and deserialization-trust review DIMER requires is what this repository implements; the review's acceptance, and the acceptance of a third-party Hub mirror as the staging source, are the maintainer's call |
| Licence | Apache-2.0 (weights and code per the upstream README's licence statement, and this repository's code) — use, modification, redistribution and commercial use permitted with the licence and notices preserved |
| Weights | Would be redistributed converted, not unmodified: the served artifact is the deterministic safetensors derived from the pinned checkpoint, with the Drive origin, the mirror revision and both digests recorded (asset spec §11.2); this repository redistributes neither |
| Remote code | **Not required** — no Hub-hosted module is imported; the model class is the vendored `modeling.py` |
| Executable serialization | One legacy torch pickle, unpickled **once** at conversion through torch's weights-only loader after a digest check and a five-stream static audit; a DIMER profile should carry the safetensors file and never the `.ckpt` |
| Runtime | `torch==2.14.0` + `numpy` + `pillow` + `safetensors`; float32; CPU is sufficient (a matte takes well under a second, an epoch about half a minute) and a GPU makes adaptation seconds |
| Upload format | `modnet-photographic-portrait-matting.safetensors` (26,135,396 bytes, SHA-256 `0ec6d832…`); **the `.ckpt` file must not be uploaded** |
| Input contract | RGB uint8 images with both sides in [64, 4096] for matting; 512 × 512 image/alpha pairs (alpha in [0, 1]) for adaptation |
| Sample data | labelled portraits rendered in code; no photograph fetched or vendored (a user's own through the notebook's photograph gate) |

**Two things are open, and neither is the licence or the code:** whether a one-time unpickle through torch's weights-only loader after a static audit with a pinned digest — in the build and in the tutorial runtime, where the notebook converts what it downloads — meets the DIMER bar, or whether DIMER should host only the safetensors converted and verified once by the maintainer (the served artifact is the same file either way); and whether a third-party Hub mirror, verified byte-identical to the authors' Google Drive release, is an acceptable provenance for a hosted profile.
